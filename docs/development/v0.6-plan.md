# v0.6 — Sections

## 1. User stories

- As a user, I can create named sections inside a project.
- As a user, I can rename or delete a section without losing its tasks.
- As a user, I can see project tasks grouped into unsectioned tasks and project sections.
- As a user, I can choose a section while creating or editing a task.
- As a user, I can create a task from a section context with the project and section preselected.
- As a user, I can identify a task's project in Today, Upcoming, and other non-project lists.

## 2. Acceptance criteria

1. A project may contain any number of non-deleted sections with non-blank names.
2. Sections are shown only inside their owning project and retain deterministic creation order after restart.
3. The project screen displays unsectioned tasks first, followed by section headings and their tasks.
4. Creating a task from a section context preselects both its project and section.
5. Task Composer shows Section whenever a project is selected and shows no selectable section for Inbox.
6. Only active sections belonging to the selected project are offered.
7. Changing the selected project clears a section that belongs to a different project.
8. Task Details autosaves valid project and section changes using the same integrity rule.
9. Deleting a section keeps every task and clears only its section assignment.
10. Deleting a project continues returning its tasks to Inbox and removes its sections through the database relationship.
11. A task cannot persist `projectId = Project A` with `sectionId = Section(Project B)`.
12. Today and Upcoming task rows show a reusable project marker combining color, icon, and accessible project name.
13. A project marker is omitted for Inbox tasks and inside the owning project screen where context is explicit.
14. Existing v0.1–v0.5 behavior and direct database upgrades remain supported.

## 3. Domain changes

- Strengthen `SectionId` into a validated value class with UUID generation.
- Add `Section` with id, projectId, name, timestamps, deletedAt, and sortOrder.
- Add `sectionId` to `TaskDraft`.
- Keep a nullable task section: null means the task is not assigned to a section.
- Treat a section without a project as invalid; selecting Inbox always clears sectionId.
- Preserve project color and icon as a single UI identity marker, as tracked by issue #17.

## 4. Database changes

- Increase Room schema from version 2 to version 3.
- Add `sections` with a foreign key to `projects.id` using `ON DELETE CASCADE`.
- Rebuild `tasks` with a foreign key from `section_id` to `sections.id` using `ON DELETE SET NULL`.
- Add a composite foreign key `(section_id, project_id)` to `(sections.id, sections.project_id)` so a task cannot reference a section owned by another project.
- Add the required unique section index for the composite parent key and indexes for ordered project sections and task section queries.
- Preserve all v2 projects and tasks; unexpected orphan or incompatible section assignments are normalized to null.

## 5. Repository changes

- Add `SectionRepository` and `DefaultSectionRepository`.
- Observe active sections by project and observe one section by id.
- Support create, rename, soft delete, and deterministic ordering.
- Delete a section and clear task assignments in one Room transaction.
- Extend task creation and updates with section assignment.
- Validate that a project exists and is active before assignment.
- Validate that a section exists, is active, and belongs to the selected project.
- Clear sectionId automatically when projectId changes to null or another project.

## 6. UI state

- `ProjectUiState` contains ordered sections and tasks grouped by sectionId.
- Project screen keeps an explicit unsectioned task group.
- `TaskDraft` contains projectId and sectionId.
- Composer derives available sections from the currently selected project.
- Task Details exposes available sections and clears incompatible local state immediately after project changes.
- Non-project lists resolve project metadata for their visible tasks so rows can render project identity.

## 7. UI components

- Section heading with name, task count, add-task action, rename action, and delete action.
- Section editor dialog or sheet with a required name.
- Section selector below Project in Task Composer and Task Details.
- Shared project identity marker combining icon and color, with project name semantics.
- Shared task-row project metadata used in Today, Upcoming, and later search/filter surfaces.

Section management stays inside the project screen. Browse continues to manage projects only. Section
reordering is not exposed in v0.6; creation order remains stable until a consistent long-press reorder
interaction is designed together with issue #18.

## 8. Navigation changes

- No new top-level destination is required.
- Section creation and editing are local project-screen overlays.
- A section add-task action opens the existing composer with projectId and sectionId preselected.
- Back from Task Details continues returning to the originating project screen.

## 9. Tests

- Domain tests cover SectionId and section-name invariants.
- DAO tests cover ordered sections, project isolation, section task queries, and deletion reassignment.
- Migration tests open v2 as v3 and verify projects/tasks plus both new foreign-key guarantees.
- Repository tests cover create/rename/delete and cross-project assignment rejection.
- Project ViewModel and Compose tests cover grouping, section management, and contextual creation.
- Composer tests cover project-dependent section options and automatic clearing.
- Task Details tests cover section autosave and project/section integrity.
- Today and Upcoming tests cover the unified project marker while project-screen tests verify its omission.
- Existing v0.1–v0.5 tests remain green.

## 10. Migration requirements

- Register an explicit `MIGRATION_2_3`; destructive fallback remains forbidden.
- Keep `MIGRATION_1_2` and verify the complete 1→2→3 upgrade path.
- Export and commit Room schema `3.json`.
- Verify schema generation in CI and keep every released schema file.
