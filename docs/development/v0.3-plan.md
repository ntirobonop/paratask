# v0.3 — Dates and Today

## 1. User stories

- As a user, I can assign an optional due date while creating a task.
- As a user, I can add a task from Today and get today's date by default.
- As a user, I can change or clear a task's due date from Task Details.
- As a user, I can see only active tasks due today in the Today tab.
- As a user, I get sentence capitalization in both title and description inputs.

## 2. Acceptance criteria

1. Quick Add in Inbox permanently displays `Дата — Не выбрана`.
2. Tapping the date control opens a date picker; selecting a date stores it on the task.
3. Quick Add in Today starts with the current local date selected.
4. The user can change or clear that contextual date before creating the task.
5. Today displays tasks where `dueDate == today`, `isCompleted == false`, and `deletedAt == null`.
6. Changing a Today task's date to tomorrow in Task Details removes it from Today after returning.
7. Completing a Today task removes it and offers the existing completion Undo action.
8. Task Details displays the current date and autosaves date changes with title and description.
9. Title and description fields in Quick Add and Task Details request sentence capitalization.
10. Dates remain persisted after application restart.

## 3. Domain changes

- Keep `Task.dueDate: LocalDate?` as the single source of truth for a task's calendar date.
- Keep `Task.dueTime: LocalTime?` nullable and preserved by all mappings and updates.
- Activate `dueDate` end to end in v0.3.
- Do not expose a standalone time control until its product behavior is specified; new v0.3 tasks keep `dueTime = null`.
- Inject a local-date provider into Today state so date-dependent tests are deterministic.

## 4. Database changes

- Keep Room schema version 1; `due_date` and `due_time` already exist.
- Add a DAO observation query for active tasks whose `due_date` equals a supplied ISO date.
- Order Today tasks by `sortOrder`, then `createdAt`, matching Inbox's deterministic ordering.
- Keep completed and soft-deleted tasks out of Today.

## 5. Repository changes

- Add `observeToday(date: LocalDate): Flow<List<Task>>`.
- Extend `createTask` with an optional `dueDate` argument.
- Persist dates as ISO-8601 text through the existing entity mapper.
- Continue using `updateTask` for autosaved date changes in Task Details.

## 6. UI state

- Extend `TaskDraft` with `dueDate: LocalDate?`.
- Extend `TaskDetailsUiState` with `dueDate: LocalDate?`.
- Add `TodayUiState` with tasks, loading state, and the contextual current date.
- Keep the selected Quick Add date local to the composer until creation.
- Task Details treats date edits as pending changes and uses the existing 500 ms autosave debounce.

## 7. UI components

- Reusable task composer with title, description, and date
- reusable date field and Material 3 date picker
- reusable task list content and task row
- reusable bottom navigation for Inbox and Today
- Today top app bar, empty state, list, FAB, and completion snackbar
- Task Details date control

Shared task-list UI moves to `core:ui` now that Inbox and Today are concrete consumers. This keeps both creation paths behaviorally identical and prevents their date controls from drifting apart.

## 8. Navigation changes

- Activate the Today bottom-navigation destination.
- Preserve the selected top-level destination while Task Details is open.
- Back from a task opened in Today returns to Today.
- Inbox and Today both open the same Task Details destination by `TaskId`.
- Upcoming and Browse remain visible but inactive until their increments.

## 9. Tests

- DAO test covers exact-date filtering plus completed/deleted exclusion.
- Repository test covers date persistence and Today observation.
- Today ViewModel tests cover loading, contextual creation date, completion, and Undo.
- Shared composer tests cover Inbox's empty date and Today's preselected date.
- Task Details ViewModel test covers due-date autosave and clearing.
- Today state tests cover a task leaving the list after its date changes.
- App integration tests cover Inbox/Today navigation and Today task visibility.
- Existing v0.1 and v0.2 tests remain green.

## 10. Migration requirements

- No Room migration is required because schema version 1 already contains `due_date` and `due_time`.
- The exported schema JSON must remain unchanged.
- CI continues checking committed Room schemas after every build.
